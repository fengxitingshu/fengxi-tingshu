## 一、播放失败：从「一失败就弹」改成「彻底救不回来才弹」

### 你遇到的现象

播放时经常弹「播放失败」，但其实再点一下又能播。

### 根因

原来的逻辑是：**只要底层报一次失败，立刻弹面板**。

但底层报失败的原因，很多只是**源站瞬时抖动**，或者**直链地址临期**。这两种情况底层其实自己会处理 —— 它会把这一集取到的直链缓存丢掉（`invalidateAudio`），下次重新解析（含自动换源）通常就能拿到新的可用直链。

结果就是：**明明能自救，却先把失败面板甩到你脸上。**

### 修复：两级处理

| 级别 | 触发条件 | 用户看到什么 |
| --- | --- | --- |
| **第一级 · 静默自救** | 同一集**第一次**失败 | **什么都不弹**，转圈继续转（让你知道还在加载），800ms 后自动重走一次播放 |
| **第二级 · 彻底失败** | 自救后**仍然**失败 | 这时才弹失败面板，给出原因和处理建议 |

### 两个细节，避免「自作聪明」

1. **每集只自救一次**。自救一轮还不行，就认定是真连不上，直接进第二级 —— 不会无限重试卡住你。
2. **自救期间你要是自己动手了，就放弃这次自救**。如果你在 800ms 内已经切了别集、换了书，或者已经开始播了，说明你已经自己处理了，重试直接取消，绝不把你从新内容上拽回去。

**计数清零时机**：一旦真正开始播放（`onPlaying`），或者你手动切集，自救计数立即归零 —— 下一集又有一次自救机会。

### 前后行为对比

| 场景 | v3.7.17 | v3.7.18 |
| --- | --- | --- |
| 源站抖一下 | 立刻弹失败面板 | 静默重试，正常播出 |
| 直链临期 | 立刻弹失败面板 | 静默重试，重新解析后播出 |
| 网络真的断了 | 弹面板 | 静默重试一次（转圈）→ 仍失败 → 弹面板 |

## 二、存储占用：查出真 bug，并且现在看得见、清得掉

### 你说的「500 多 M」

核对结论：**里面确实藏着一个真 bug**，另有一部分是大头音频缓存和固定开销。

### 真 bug：缓存上限从来没生效过

App 里有个「缓存上限」设置（默认 2048 MB）。但它的执行点只有一个：

```
CacheManager.cacheBook()          ← 「整本缓存」这个功能才会走到这
        ↓
   CacheRepo.enforceLimit()       ← 清理超限缓存，只有这一条路会调用
```

问题在于：**日常根本没人走这条路。**

平时真正在跑的是「边听边预读」：

```
autoCacheAhead()   →  cacheChapter()  →  downloadOne()
  每播一集，自动往后预读 3 集
```

这条路上**从头到尾没有一次容量检查**。于是：

> **一边不停往回存，一边从来没人清理。**

单集音频约 10~15 MB，听一下午就能把存储顶到几百 MB。这就是你报「占了 500 多 M」的直接原因之一。

**修复**：在 `cacheChapter()` 里 —— 也就是**每一集缓存完成之后** —— 顺手跑一次容量上限。现在上限立即生效，存到上限就自动从最旧的开始清。

### 500 MB 都是什么（实测构成）

| 组成 | 大小 | 说明 |
| --- | --- | --- |
| **音频缓存** | 大头（默认上限 2048 MB） | 可清理，你现在看到的大部分是它 |
| 应用数据 | 与音频缓存同级 | 封面、详情页缓存等 |
| APK 安装包 | 约 18 MB | 固定开销 |
| 解压出的 .so 库 | 约 8 MB | 固定开销（`extractNativeLibs="true"`） |
| Python 运行时 | 约 7 MB | 固定开销（书源解析用） |
| 临时缓存 | 约 10 MB | 可清理 |
| 书源 / 插件 | 几 MB | **不可清理**（清了源就没了） |

> 结论：**除了那个 bug，其余没有异常** —— 主要就是音频缓存本身。它是设计成可配上限的，上限默认 2048 MB 偏宽松。

### 新增：存储占用可视化 + 一键清理

**设置 → 存储占用**

- 自动统计，显示**合计约 X MB**
- 展开明细：音频缓存 / 应用数据 / 临时缓存 / **书源插件（标注不可清理）** / Python 源 / Python 运行时 / 安装包
- 「刷新」按钮可手动重算

**设置 → 一键清理缓存**

- 弹确认框 → 清掉：**音频缓存 + 封面 + 详情缓存 + 临时缓存**
- **绝对不动**：书源、JS 插件、Python 源、Python 运行时、数据库
- 清完提示「已释放 X MB」，并自动重算存储占用

> 想立刻把空间压下来：先去设置把「缓存上限」调小（比如 512 MB），再点一次「一键清理缓存」。

## 四、选集 3 列溢出屏幕：根因找到并修掉

### 现象

选「3 列」时，第 2、3 列跑到屏幕外面去了。

### 根因：CSS Grid `1fr` 的隐藏陷阱

这是本次最有意思的一个坑。

原来的写法：

```css
grid-template-columns: 1fr 1fr 1fr;
```

看起来是「三等分」。但 **`1fr` 其实是 `minmax(auto, 1fr)` 的简写**，而那个 `auto` 最小值**不会小于内容的 min-content 宽度**。

章节名是很长的中文串，**中间没有空格、不可断行** —— 所以它的 min-content 宽度 **就是整串文字本身的宽度**。实测：

```
单个长章节名的 min-content 宽度 ≈ 375px
→ 每列被强行撑到 375px
→ 3 列 = 1125px
→ 容器只有 393px，第 2、3 列直接被挤到屏幕外
```

实测数据：`scrollWidth = 1132`，容器 `393` —— 完全对上了。

### 修复：两件事必须同时做，缺一不可

```css
/* 1. 轨道显式写 minmax(0, 1fr) —— 允许列被压到比内容更窄 */
grid-template-columns: minmax(0, 1fr) minmax(0, 1fr) minmax(0, 1fr);

/* 2. 子项补 min-width: 0 + overflow: hidden —— 允许子项被压缩 */
.chitem { min-width: 0; overflow: hidden; }
```

**只改轨道不改子项，或者只改子项不改轨道，都修不好。** 这和 flex 里的 `min-width: 0` 是完全同一类问题。

同时给容器加了 `box-sizing: border-box`，并收紧了字号与内距（`12.5px` / `padding: 11px 8px`），让 3 列排得下且好看。

### 实测（4 种机型 × 2 列 / 3 列）

| 屏幕宽 | 2 列溢出 | 3 列溢出 |
| --- | --- | --- |
| 320px | 0 | 0 |
| 393px | 0 | 0 |
| 412px | 0 | 0 |
| 768px | 0 | 0 |

393px 屏下：每列 127px，第 3 列右边缘 387 ≤ 393 ✓ 正好**和屏幕等宽**。

实测 3 列下长名字：动画 `mqScroll` / `running`，周期 11.47s；短名字保持静止 ✓
